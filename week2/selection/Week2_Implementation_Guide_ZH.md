# 第2周实施说明：代码依赖与证据组选取预实验

适用项目：长上下文代码 Transformer 的高效注意力研究。投入预算：35小时。

这是原计划“第2周”的任务包。日期已到2026年11月10日，下面按接下来5个工作日执行，不把原定日期当作已完成进度。你后来明确过：4层 Transformer 用于验证可行性，后续可能迁移到约7B的开源模型。本文没有假定你已完成第1周的代码。

## 1. 本周回答什么问题

**在相同信息访问预算下，把相关代码块作为证据组选择，是否比独立选块更容易保留完整证据，并帮助同一个模型答对问题？**

把这个问题分成两步：

1. 选取实验：分析器是否找对依赖，选择器是否满足预算，是否保留定义、参数来源、返回值和条件信息。
2. 模型实验：固定模型权重，用不同策略提供的代码内容预测同一答案，比较准确率。

第一步可以用CPU和Python标准库完成。第二步需要你的4层模型或已经跑通的其他骨干。附带原型已实现第一步及模型输入接口，没有训练好的神经模型。证据覆盖率不能当成模型准确率；上下文选取原型也不能直接证明稀疏Attention加速。

## 3. 数据怎么做

主任务定为：**读一段Python代码，预测最后变量 `result` 的整数值。** 先覆盖三类依赖：

| 类型 | 需要的信息 | 验证目的 |
|---|---|---|
| 赋值链 | `a → b → c → result` | 能否沿变量定义追溯 |
| 函数调用 | 实参来源、函数定义、返回表达式、返回表达式引用的全局值 | 能否保留跨函数证据 |
| 条件返回 | 上述信息，加上影响返回的条件及条件来源 | 能否保留控制依赖 |

例如：

```python
base = 7
limit = 5
bonus = 3

def adjust(p):
    if p > limit:
        return p + bonus
    else:
        return p - bonus

unused = 100
value = adjust(base)
result = value + 1
```

这个例子的答案为11。选择器只能读代码及查询位置，不能读答案11。

`result` 需要 `value`；`value` 需要函数 `adjust` 和实参 `base`；函数计算又需要 `limit`、`bonus`。`unused` 不影响结果。

原型在生成时记录哪些语句属于这条构造链，并用随机名称、随机常数和无关赋值打乱位置。标签由生成规则算出，测试会独立执行**本地固定生成器生成的代码**核对答案。分析器和选择器本身不执行输入程序。

这里的 `gold_static_spans` 是**保守静态证据标注**：条件函数的两个分支都包括在内。它不是执行时最小证据集，也不是因果最小证明。统计“全部保留”时，必须保留这一整套保守证据。

附带300条属于 `smoke_only`，只检查流程。正式做模型实验时，另建训练/验证/测试集，不能拿这300条同时训练和报告测试成绩。初始可用2000/300/300条作为调试规模，样本不足再按验证集表现扩充。近似模板、改名版本和反事实成对样例应按同一源模板分组，整体划入同一个集合。只有改变随机数的拆分只能说明模板内表现；模板外测试需新增结构模板并整组留出。

## 4. 依赖分析怎么实现

第一版只支持很小的Python子集：

- 模块级单变量赋值；每个名字只绑定一次。
- 整数、简单算术与比较表达式。
- 具名函数的普通位置参数调用。
- 函数体是一条 `return`，或一个带双分支 `return` 的 `if/else`。
- 函数可以读取调用前已定义的全局整数变量。

循环、递归、类、属性访问、容器索引、默认参数、闭包、重绑定等会明确报错。这是原型的范围，不是通用Python程序依赖图工具。

用Python内置 `ast.parse(code)` 获取语法树。AST提供语法节点和源码位置，依赖边需要自己添加。源码位置的列偏移是UTF-8字节偏移，因此原型统一用字节定位，避免中文变量名导致位置错位。[1]

实现思路：

1. 第一遍扫描顶层语句，建立 `变量名/函数名 → 定义节点` 的表。
2. 扫描赋值右侧读取的名字，添加“当前赋值 → 该名字的定义”边。
3. 遇到函数调用，分别添加“调用结果 → 函数定义”和“调用结果 → 实参来源”边。
4. 扫描函数的返回值与条件中读取的全局名字，分别标注返回值依赖、控制依赖。
5. 从 `result` 反向遍历依赖，计算每个节点距目标的步数。

例子中的粗粒度图可以写成：

```text
result 的依赖：value
value 的依赖：adjust（调用返回）、base（实参来源）
adjust 的依赖：limit（条件）、bonus（返回值）
```

原型把一个短函数整体作为一个语义节点，再映射到固定大小的token块。它能保留函数里的条件与返回信息，但**尚未把函数内部每一个语句拆成独立PDG节点**。参数名 `p` 仅在函数内部生效；实际输入通过每个调用点的实参边表达，避免把不同调用的参数混到一起。

先读 `analyze()`，再看 `test_argument_control_and_return_edges`、`test_parameter_shadows_global` 和 `test_calls_do_not_merge_arguments`，就能理解主要逻辑。

## 5. 代码如何变成块与候选组

原型明确采用字节分词：一个UTF-8字节是一个token，普通token编号0–255，另保留PAD=256、读出符CLS=257。这样第一版不需要下载分词器，也能精确核算这个原型自身的token预算。

默认每64个字节token一块。包含 `result` 查询语句的块，以及最后一个块，组成固定本地集合 `L`。它们对三种方法都可见。远端预算另计：128、256、384个字节token。

对每个语义节点作为锚点，沿依赖边回溯最多2步，把这些节点覆盖的块合并，即得到一个候选证据组。构造时不读答案和gold标注。跨块语句必须映射到它实际覆盖的所有块，不能只按起始行算一个块。

同一块可以属于多个组。例如：

- 已选集合 `S = {B1, B2}`。
- 候选组 `G1 = {B2, B3, B4}`。
- 添加 `G1` 只新增 `B3、B4`，成本是2块，不是3块。

对应代码：

```python
new_blocks = group_blocks - selected_blocks
new_cost = sum(block_token_lengths[b] for b in new_blocks)
```

这里的字节token不是Qwen/DeepSeek的token。接入已有模型时，必须改用该模型实际分词与源码位置映射，并重新统计预算。不能把“384字节token”写成“384个Qwen token”。

## 6. 三种选择器如何公平比较

| 名称 | 使用的信息 | 如何选 |
|---|---|---|
| `lexical_topk` | 查询与块的词法重合 | 对块独立评分，按分数选择 |
| `structure_topk` | 依赖图、同一套候选组及权重 | 将组权重分配给成员块，再逐块选择 |
| `evidence_groups` | 与结构Top-k相同的图、组、权重 | 选择能以较小新增成本完成更多高权重组的集合 |

第一个是弱的词法Top-k，用于检查流程；它不是MoBA、NSA等论文的正式复现，也不是学习式单块选择器。关键比较是第二个与第三个，否则很容易把“额外使用结构信息”的收益误当成“分组选择”的收益。

本周先使用固定打分：锚点距目标越近，权重越高；与目标不连通的锚点权重为0。

```python
weight = 1 / (1 + dependency_distance)
```

结构Top-k把一个组的权重平均分给成员块，再累加每个块的分数。证据组方法维护集合S，计算加入一个组后新完成了哪些候选组，用“新完成组的总权重 / 新增token数”排序，每轮选一个能放进剩余预算的组。没有完整组能加入时，用结构Top-k的同一个排序规则填补剩余预算。

这是一种考虑共享成本的贪心启发式，不是最优联合搜索，也尚未学习查询表示。它用于把接口和预算逻辑做对，后续才能替换成可训练评分器。

公平条件：相同原始代码、查询、块划分、本地集合、候选块全集、远端预算。三种方法都从源码推导信息，禁止把测试答案、gold证据、实际运行分支输入选择器。完整代码可作为无预算参考，但不能称为同预算基线。

## 7. 怎样接到4层Transformer

如果你的4层模型已经可以训练，保留骨干，先替换输入可见内容。示例接口：

```python
from week2_mvp import analyze, select
from model_adapter import pack_selected

analysis = analyze(code, block_size=64)
selected = select(analysis, "evidence_groups", budget=256)
packed = pack_selected(analysis, selected)

# packed["input_ids"]：真正送给模型的token
# packed["position_ids"]：这些token在原始源码中的位置
# packed["readout_index"]：用于预测答案的CLS位置
# 由你的模型训练/评估代码完成张量化、padding、forward与答案预测。
```

模型第一层之前就应移除未选中的token，并保留选中token的原始位置。不要先对完整代码跑多层模型，最后才遮住部分块：未选代码的信息可能已经进入保留下来的隐藏状态，使实验失效。`pack_selected()` 不把答案、gold标注传入模型。截取后的token片段可能不是合法Python，这不影响作为模型输入；不要执行这些片段来评价神经模型。

先用完整代码训练和检查任务是否能学会。模型连完整代码都答不好时，先检查数据、标签、训练和任务难度，不能根据三种策略都很差就判定选组无效。可先检查能否拟合几十个固定样例，再检查独立验证集。

正式比较时使用**同一份checkpoint**，对每个测试样例分别运行三个输入版本。若仅用完整代码训练，选取后的输入可能存在分布变化，需要说明；更充分的验证可用全代码及多种选取视图混合训练一份共享模型，视图采样不能依据gold标签选优。不要只为组方法专门训练，然后与未适配的其他方法比较。

本周若从头搭建，建议先固定4层、隐藏维度128、4个头、FFN维度512，使用小上下文检查管道。它们是调试起点，不能保证足够任务准确率。上下文上限应覆盖原始位置索引；压缩输入后仍保留原始位置，不能只按压缩后的长度设位置表。PyTorch的TransformerEncoder可以堆叠多层；官方文档提醒，构建后应注意各层参数初始化。[2]

若后续直接修改Attention，所有层都需要遵守同一信息访问规则，并保持正确的因果约束。PyTorch SDPA的布尔mask中True表示允许参与注意力；它与某些其他mask接口的含义相反。[3] 当前包采用输入选取接口，没有实现或测量真正的块稀疏执行。

## 8. 结果表应记录什么

| 指标 | 含义与注意点 |
|---|---|
| 静态证据完整率 | 所有标注的保守静态证据块都保留的样例比例 |
| 远端证据召回率 | 需要的远端证据块中保留了多少；本地块不混进分母抬高分数 |
| 预算可行比例 | gold所需远端块本来就装得下的样例比例 |
| 可行样例完整率 | 只在预算装得下全部标注证据的样例上统计完整率 |
| 答案准确率 | 同一模型真正预测正确的比例，附带原型没有测量这一项 |
| 实际使用token数 | 记录实际选择，不只记录预算上限 |
| 分析与选择耗时 | 分别计时，后续计入端到端成本 |
| 模型推理耗时与峰值显存 | 接入模型后另测；缓存、预热、设备、batch等条件一致 |

GPU推理计时需要正确同步，不能只量到异步提交时间。缓存依赖图的场景应同时说明首次分析成本和复用成本。一个稠密mask也不能自动证明计算量按可见块数下降；真实加速要另测执行实现。

模型结果建议按同一测试样例配对比较，并看任务类型、预算及随机种子。调参看验证集，不用测试集反复挑最有利结果。

## 9. 随包附带的实际检查结果

本次已运行：10项自动检查全部通过，300条生成样例，3种预算，3种选择器，共2700条选择记录。测试中的90条生成样例还核对了程序输出与标签，以及分析器证据与生成器独立标注的一致性。

聚合静态证据完整率如下：

| 远端字节token预算 | 词法Top-k | 结构Top-k | 证据组 | 全部静态证据可装下的比例 |
|---:|---:|---:|---:|---:|
| 128 | 3.3% | 10.0% | 10.0% | 10.0% |
| 256 | 28.0% | 68.0% | 68.0% | 68.0% |
| 384 | 68.7% | 97.3% | 97.3% | 97.3% |

**这些是本次生成样例上的程序运行结果，不是你的模型成绩，也不是公开benchmark结果。**

结构Top-k与证据组在这批简单任务上持平：因为依赖分析已经准确圈定目标所需的全部静态证据，预算够时，逐块选取也能选齐；预算不够时，没有方法能保留所有标注证据。不能据此宣称分组策略优于结构逐块选择。

这个结果提示下一步的实验设计：如果希望检验“联合分组”的价值，需要研究更接近实际的多个候选解释、保守分析带来的额外分支、共享证据和查询相关性不确定等情况，并仍给逐块基线相同的信息。扩展这些情况需要同时扩展生成器、分析器及独立标注；不能仅给组方法额外gold信息或故意削弱对照。也可以用人工审查的小型真实代码集检查当前受限解析器能覆盖哪些情况。

若更强、信息相同的基线仍然持平，这是需要记录的研究发现；下一步应调整假设与任务，不能通过持续挑选有利样例制造优势。
