# Week 3 — Attention-Visibility Experiments with a Frozen Qwen

Scope: efficient attention for long-context code. Follows on from the Week 1–2 report.

**Summary for the reader in a hurry.** We attached the Week-1 synthetic task and the Week-2 dependency analysis to a frozen Qwen2.5-Coder-3B-Instruct and compared six attention-visibility patterns under identical weights, programs and answer readout. Three things are established. (1) The Week-1 three-hop task is at chance for this model (15%, indistinguishable from random), so it cannot be used to compare attention patterns; a one-hop task with a controllable distance is needed. (2) On that one-hop task, full attention still answers correctly with the defining statement 4,051 tokens away (98%), so distance *per se* does not damage the ability under study. (3) Restricting each query to the previous 64 tokens drops accuracy to 0–16%, and placing the same *number* of visible tokens at random positions does no better or worse than a local window — the loss comes from the visibility budget, not from the shape of the pattern. The central result is that an oracle mask that keeps every evidence token directly visible restores full accuracy only up to ≈450 tokens of distance; at 1,646–4,051 tokens it restores just 18–22%. Holding sequence length fixed at 4,051 tokens and moving the definition next to the query instead lifts the same masks from 0% to 90% (window=64) and from 18% to 72% (oracle). The failure is therefore caused by **distance**, not by the length of the masked sequence. A window sweep shows that recovery requires a window of the same order as the distance (at 4 k tokens: 25% of connections → 78%). **Conclusion: post-hoc attention masking cannot preserve long-range retrieval in a frozen model; Week 4 has to adapt the model during training.**

---

## 1. Questions for the week

1. At what task difficulty does a frozen Qwen still have headroom? (Decides which dataset the comparison can use.)
2. Does distance itself damage performance? (Decides whether "long context" is a controllable variable.)
3. When the visible range changes, how much ability remains — and is the loss caused by *seeing fewer tokens* or by *seeing the wrong ones*?
4. If only the evidence tokens are guaranteed visible (an oracle), how much comes back?

## 2. Setup

### 2.1 Data

Two datasets, for two different purposes.

**A. Week-1 three-hop programs** (`week1/data/`, fully audited: 2,100/2,100 labels verified against CPython). Test split: 540 programs at 256/512/1,024 bytes, 180 per length and 60 per dependency family, balanced over answers 0–9. Used to measure the ceiling and to decide whether the task is learnable at this model scale.

**B. Distance-controlled needle programs** (generated by `week3/w3_needle.py`). Each program contains exactly one dependency chain: a definition `n050000 = 7` at one end, a block of irrelevant assignments, and `result = n050001` at the other. The number of hops controls reasoning depth; the number of filler lines controls the **token distance** between the definition and the readout. The two factors are independent. Labels are re-checked by the Week-1 interpreter. The main table uses one hop and five target distances (20/100/400/1,600/4,000 tokens), 50 programs per cell; the realised prompt lengths are given as the `distance` column of each table.

The same generator can emit `--position end` variants: identical length, but the definition sits immediately before `result`. This separates "distance" from "sequence length".

### 2.2 Model and answer readout

| Item | Value |
|---|---|
| Model | Qwen2.5-Coder-3B-Instruct (36 layers, hidden 2,048, 16 heads / 2 KV heads) |
| Weights | frozen; no training of any kind |
| Precision / device | bfloat16, RTX 4000 Ada 19.5 GB, torch 2.6.0+cu124, transformers 4.57.1 |
| Prompt | program + `\nprint(result)\n# Output:`, followed by one space token |
| Readout | softmax over the ten digit tokens at the position after that space; take the arg-max |
| Positions | no explicit `position_ids`; sequence order as usual |

One implementation detail has to be stated because it decides whether any number in this report is meaningful. Qwen's tokenizer splits every digit into a separate token, and the trailing space of `# Output: ` is a token in its own right (id 25). Scoring `logits[-1]` over the digit tokens therefore compares `"7"` rather than `" 7"`, i.e. a different position from the model's natural continuation. The `leak` gate level below exists to expose exactly this mistake.

### 2.3 Six visibility patterns

All patterns change the mask only; the token sequence is identical across conditions, so every comparison uses the same input ids.

| Pattern | Definition | Nature |
|---|---|---|
| `full` | causal, everything visible | ceiling |
| `window=W` | each query sees the previous W positions | local attention |
| `window=256` | as above, W = 256 | identity check against `full` when the sequence is shorter than 256 |
| `random=W` | the same W visible positions per row, drawn uniformly with a per-item seed | **same budget, random placement** control |
| `block=4` | one block per four source lines, blocks never see each other | true cut-off (stacking layers cannot relay across blocks) |
| `gold_union=W` | window ∪ all gold evidence tokens made global | **oracle upper bound**, uses gold annotations; not a deployable method |

`gold_union` answers the question "how much is lost even if the evidence is guaranteed visible". It is not a method and is never compared against methods as if it were one.

Masks are passed as 4-D boolean tensors to `model(attention_mask=...)`, `True` meaning "may attend". This path was verified on transformers 4.57.1: an explicit full mask reproduces the unmasked output to within 1e-4, and a window mask changes the logits. Both properties are pinned by automated tests.

### 2.4 Metrics

- Accuracy: exact match over ten classes; Wilson 95% intervals in brackets where useful.
- Distance: tokens from the readout to the earliest evidence token (`gold_gap`).
- Connections: allowed (query, key) pairs. This is a logical quantity, not FLOPs and not a speed-up.
- 50 programs per cell (20 per family for the three-hop curve). **Differences below ±10 percentage points at n = 50 are not interpreted.**

### 2.5 Gate

Before comparing any masks, three levels must pass; otherwise the run stops.

| Level | Construction | Pass line |
|---|---|---|
| `trivial` | one line, `result = x + y` | ≥ 80% |
| `leak` | a real program with the answer written into a comment | ≥ 80% |
| `real` | the actual 256-byte programs | recorded only |

## 3. Results

### 3.1 Gate and ceiling

**Table 1 — Gate (n = 40)**

| Level | Accuracy | Wilson 95% | Reading |
|---|---:|---|---|
| `trivial` | 90% | 77–96% | readout works |
| `leak` | 93% | 80–97% | a visible digit can be copied |
| `real` | 15% | 7–29% | the three-hop task is already near chance |

`leak` at 93% shows the bottleneck is not the readout. `real` at 15%, with an interval that straddles 10%, shows that the **three-hop task has no ceiling for this model**.

**Table 2 — Ceiling curve on the three-hop task (20 per family)**

| Source bytes | n | Accuracy | assignment chain | function call | conditional return |
|---|---:|---:|---:|---:|---:|
| 96 | 40 | 23% | 5% | 40% | — (generation failed) |
| 160 | 53 | 30% | 10% | 25% | 69% (n = 13) |
| 256 | 60 | 20% | 20% | 15% | 25% |
| 512 | 60 | 7% | 10% | 5% | 5% |

No cell is close to usable. **This task cannot support a comparison of attention patterns**: on a 20% baseline no mask difference could be interpreted.

### 3.2 Depth is the bottleneck; distance is not

**Table 3 — Full attention, depth × distance (n = 20 per cell)**

| Hops | 73 tok | 216 | 736 | 2,816 |
|---|---:|---:|---:|---:|
| 1 | 100% | 100% | 100% | **100%** |
| 2 | 45% | 20% | 20% | 30% |
| 3 | 20% | 5% | 5% | 5% |

One hop is solved perfectly even at 2,816 tokens, i.e. the model handles long-distance single-hop retrieval. Two hops collapse to 20–45% and three hops to chance. **Depth, not distance, is the limiting factor.** This is why every subsequent experiment uses one-hop data.

### 3.3 Visibility comparison

**Table 4 — Six visibility patterns × five distances (n = 50, one hop)**

| Distance (tok) | full | window=64 | window=256 | random=64 | gold_union=64 | block=4 |
|---:|---:|---:|---:|---:|---:|---:|
| 73 | 98% | 68% | 98% | 80% | 98% | 6% |
| 151 | 100% | 6% | 100% | 12% | 100% | 8% |
| 450 | 100% | 16% | 16% | 8% | 100% | 10% |
| 1,646 | 100% | 6% | 14% | 12% | **22%** | 14% |
| 4,051 | 98% | 0% | 12% | 8% | **18%** | 4% |

Three observations.

1. `full` is still 98% at 4,051 tokens: **distance per se does not damage the ability**.
2. At distance 73, `window=256` equals `full` because it covers the whole sequence — the control is wired correctly.
3. Up to ≈450 tokens, accuracy depends almost entirely on whether the distant definition is inside the visible set: inside (`gold_union`) gives 98–100%, outside (window or random) gives 6–16%. From 1,646 tokens on, **even the oracle falls to 18–22%**.

`block=4` stays at 4–14%, the expected behaviour of a true cut-off.

### 3.4 The loss comes from the budget, not from placement

**Table 5 — Local window versus random placement at the same connection count (n = 50)**

| Distance (tok) | window=64 | random=64 | Connections (both) |
|---:|---:|---:|---:|
| 73 | 68% | 80% | 2,656 |
| 151 | 6% | 12% | 7,648 |
| 450 | 16% | 8% | 26,784 |
| 1,646 | 6% | 12% | 103,328 |
| 4,051 | 0% | 8% | 257,248 |

Every cell is within ±10 points, i.e. within noise. **Knowing which positions to attend to is no better than attending to the same number of random positions**: at a 64-token budget, what decides success is whether the evidence happens to be inside it, not the shape of the pattern.

### 3.5 The failure is distance, not sequence length

**Table 6 — Same 4,051-token sequences, only the position of the definition changes (n = 50)**

| Condition | Distance (tok) | full | window=64 | gold_union=64 | random=64 |
|---|---:|---:|---:|---:|---:|
| definition at the start | ≈4,040 | 98% | **0%** | **18%** | 8% |
| definition next to the query | ≈46 | 98% | **90%** | **72%** | 14% |

Length, mask structure and total token count are identical; only the position of the definition moves. `window=64` goes from 0% to 90% and `gold_union=64` from 18% to 72%. **The collapse at 4 k is caused by distance, not by "a long sequence under a sparse mask".**

One counter-intuitive detail: at distance 46, `window=64` (90%) is above `gold_union=64` (72%). The two Wilson intervals overlap, so we treat this as noise for now. If it survives at 100 programs per cell, it would mean that making whole gold rows visible dilutes attention, which deserves its own note.

### 3.6 Recovery requires a window of the same order as the distance

**Table 7 — Window sweep at 4,051 tokens (n = 50)**

| Pattern | Connections | Share of full | Accuracy | Wilson 95% |
|---|---:|---:|---:|---|
| `full` | 8,207,326 | 100% | 98% | 90–100% |
| `gold_union=64` | 403,867 | 4.9% | 18% | 10–31% |
| `gold_union=128` | 654,651 | 8.0% | 24% | 14–37% |
| `gold_union=256` | 1,143,931 | 13.9% | 60% | 46–72% |
| `gold_union=512` | 2,073,339 | 25.3% | 78% | 65–87% |

Monotone and steep. The same sweep at 1,646 tokens gives 22/40/58/62% — same direction, lower absolute level; with 50 programs per cell and overlapping intervals we draw no conclusion from the cross-distance comparison.

The implication is direct: **the window has to be of the same order as the dependency distance**, not merely "the evidence must be visible". At 4 k tokens, recovering to 78% costs 25% of the connections — not an attractive efficiency ratio, especially since masking does not save computation at all.

### 3.7 Two controls that turned out to be uninterpretable

| Experiment | Result | Why it cannot be used |
|---|---|---|
| Counterfactual / deletion on three-hop 256 B (n = 180) | 14.4% / 8.9% | the task itself is at 15%; there is no signal to lose |
| 4 KB visibility on three-hop data (n = 60) | full 3.3%, window 10%, oracle 1.7% | full attention is already at chance |

Neither is used in any conclusion. They are recorded here only as "uninterpretable on a sub-task without a ceiling".

## 4. Conclusions

### 4.1 Established

1. **No ceiling on the three-hop task at 3B**: 15% overall (7–29%), 7–30% by length, indistinguishable from random. The Week-1 data cannot support an attention comparison.
2. **The one-hop task has a reliable ceiling and a controllable distance**: full attention holds 98–100% from 73 to 4,051 tokens.
3. **The loss under a sparse mask comes from the visibility budget, not from placement**: a random mask with the same per-row budget matches a local window (Table 5).
4. **The recovery power of post-hoc masking decays with distance**: oracle evidence visibility gives 100% up to ≈450 tokens and only 18–22% at 1,646–4,051 tokens (Table 4).
5. **That decay is caused by distance**: at constant sequence length, moving the definition next to the query takes `window=64` from 0% to 90% (Table 6).
6. **Recovery needs a window comparable to the distance**: at 4 k tokens, 4.9%/13.9%/25.3% of connections give 18%/60%/78% (Table 7).
7. **The measurement pipeline is reproducible**: 24 automated tests (including "explicit full mask == no mask" and "random=W has the same per-row degree as window=W"), tokenizer and data shipped with the repository, works offline.

### 4.2 Not established

1. **Mechanism.** We did not measure attention weights this week. "The model uses the intervening context as scaffolding" is consistent with the data but is not evidence for it.
2. **Real code.** Everything here is synthetic. The dependency-distance distribution of real repositories is unknown, so whether "window 512 + a few global anchors" is enough in practice is not answered.
3. **Whether training fixes it.** Not attempted; this is the Week-4 question.
4. **Speed.** No sparse kernel was tested. All "connection" figures are logical; under dense SDPA a mask neither saves computation nor speeds anything up (already measured in Week 1: 56.5–87.9% fewer connections, essentially unchanged wall-clock).

## 5. Threats to validity

| Threat | Effect | Handling |
|---|---|---|
| 50 programs per cell | differences below ±10 points are uninterpretable | Wilson intervals everywhere; no cross-distance claims |
| A single model scale | conclusions may hold only for 3B | stated explicitly; 1.5B runs pointed the same way but were not systematically compared |
| Synthetic grammar | real code may have very different distance distributions | described as diagnostic data only; the link to real code is deferred to Week 4 |
| Oracle uses gold annotations | `gold_union` is not a deployable method | labelled as an upper bound throughout, never ranked against methods |
| Programs reused across conditions | conditions are paired, but no paired test is reported | tables give per-cell accuracy only; paired testing deferred to the formal analysis |
| Masking does not save compute | "connections" invites reading it as a speed-up | every table and caption says logical connections, not FLOPs |
| 3B rather than 7B | the lab home quota (16 GB free) cannot hold 7B weights | stated in §2.2; a 7B replication is future work |

## 6. What this means for Week 4

This week narrows the route.

1. **Stop tuning mask parameters.** With frozen weights, the long-distance loss cannot be repaired by making evidence visible.
2. **Move to training-time adaptation.** Sparse-attention models in the literature are trained, not masked post hoc; our data show the two are not the same thing. Minimal viable experiment: LoRA-tune Qwen2.5-Coder-3B while training *with* the `window=64` / `gold_union=64` masks, and see whether the 18% at 4 k can be brought above 80%.
3. **Bring in the Week-2 analyser.** If most dependencies in real code are shorter than 512 tokens, then "window 512 + a few global anchors" is adequate in practice — a stronger claim than "no loss on a synthetic task", and it explains why the 4 k results here are pessimistic.
4. **Optional attention probe.** Under `full`, measure the attention mass from the readout onto the gold tokens as a function of distance. If it is high below 450 and collapses beyond 1,646, the "scaffolding" reading in §4.2 gains direct support.

## 7. Reproduction

```bash
# 0) environment self-check (no weights needed)
python lab_check.py
python -m unittest -v test_week3          # 24 tests

# 1) gate
python w3_gate.py --model <3B> --style completion --limit 40

# 2) ceiling on the three-hop task

# 3) depth x distance

    --group-by family_id --modes full --no-reach --out results/needle_full

# 4) visibility (main table)
python w3_needle.py --distances 20 100 400 1600 4000 --hops 1 --per 50 --split needle_long
python w3_run.py --model <3B> --data-dir data --split needle_h1 --lengths 0 \
    --group-by family_id --no-reach \
    --modes full,window=64,window=256,gold_union=64,block=4,random=64 \
    --out results/vis_h1

# 5) same length, short distance
python w3_needle.py --distances 4000 --hops 1 --per 50 --position end --split needle_end
python w3_run.py --model <3B> --data-dir data --split needle_h1_end --lengths 0 \
    --group-by family_id --no-reach \
    --modes full,window=64,gold_union=64,random=64 --out results/vis_end

# 6) window sweep
python w3_run.py --model <3B> --data-dir data --split needle_h1 --lengths 0 \
    --group-by family_id --no-reach \
    --modes full,gold_union=64,gold_union=128,gold_union=256,gold_union=512 \
    --out results/vis_goldwin
```

Every number in this report comes from the commands above, run on an RTX 4000 Ada (19.5 GB); the whole set takes about 25 minutes. Per-item records are in `results/` (`summary.csv` per group, `per_item.csv` per program).

## Appendix A — Definitions

- Accuracy: per-program exact match over ten classes.
- Distance: tokens from the readout (last token) to the earliest evidence token.
- Connections: allowed (query, key) pairs; not FLOPs, not a speed-up.
- Intervals: Wilson 95%; no bootstrap, no paired test.
- `gold_union`: oracle upper bound using gold annotations; not deployable.
- `random=W`: exactly the same number of visible positions per row as `window=W`, drawn with a seed derived from the program id and fully reproducible.
- Receptive field: `RF = 1 + L × (W − 1)`; with 36 layers and W = 64, RF = 2,269 tokens.
